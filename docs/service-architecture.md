# 服務架構

**建立日期：2026-08-06**

> `functional-architecture.md` 講「系統做哪些事」，這份講「客戶買到什麼、誰交付、什麼時候交付」。
> 兩份的差別是主詞：那份的主詞是系統，**這份的主詞是人。**

---

## 0. 一個前提：這不是自助 SaaS

比對 `skills-inventory.md` 之後可以確定一件事（`open-questions.md` E14）：

**協會腦建不起來，整個工具就沒有價值**——事實庫是空的，系統只會吐一堆 `【請補資料】`。
而協會腦的建檔是靠 `npo-org-brain` 這支**對話層 skill**，跑的人是顧問，不是協會。

所以服務架構的第一條：

> **第一年一定含人工導入。工具是顧問的放大器，不是顧問的替代品。**

這不是妥協，是定價權的來源。純工具的天花板是月費，帶顧問才有年約。

## 1. 服務全景

```
   獲客           導入            日常產能         回看交代        方向與續約
 ┌────────┐   ┌────────┐      ┌────────┐      ┌────────┐      ┌────────┐
 │ 免費健診 │──▶│ 協會腦   │──▶  │ 工具訂閱 │──▶  │ 成效月報 │──▶  │ 年度規劃 │
 │  M1     │   │ 建檔     │     │ M3/M4/M5│     │  M6     │     │  M2     │
 └────────┘   └────────┘      └────────┘      └────────┘      └────────┘
     免費        一次性導入費        月費          （含在月費）      年度顧問費
      │             │                │                │              │
   顧問跑 skill   顧問 ＋ 協會      協會自己用       工具自動        顧問帶工作坊
   ~1 小時       ~2 週              每週            每月             每年 ＋ 每季
                                                                        │
                                                    ┌───────────────────┘
                                                    ▼
                                            回到年度規劃，續約
```

**四個收費點，三種收費形態**：免費（健診）／一次性（導入）／月費（工具）／年費（顧問）。

## 2. 四層服務

### L0 免費健診 — 漏斗入口

| | |
|---|---|
| **誰做** | 顧問跑 `npo-fundraising-audit`（含 Step 0 公開資料逆向偵察） |
| **投入** | 約 1 小時，其中大半是 skill 自動跑 |
| **協會要付出** | 填一份約 20 題問卷，或什麼都不用給（逆向偵察可先跑） |
| **交付** | 一份診斷報告：曝光／認同／捐款率三段診斷、缺口排序、前三優先動作 |
| **收費** | 免費 |
| **為什麼免費** | 這份報告本身就會讓協會發現自己的問題。問題被看見，才有後面的成交。 |

**關鍵設計**：報告末頁要有雙導流——「缺口交給我們每天顧」（顧問）／「用工具自己顧」（訂閱）。
這在 `skills-inventory.md` §1.2 已列為要改的項目。

> 逆向偵察可以在協會**還不知道你是誰**的時候就先跑。
> 帶著一份「我已經看過你們官網、社群、捐款頁」的報告去談，成交率是完全不同的量級。

---

### L1 導入 — 一次性 ★ 目前所有文件都沒有這一層

這是四份上游文件裡完全沒被寫出來、但實際最重的一段。

| | |
|---|---|
| **誰做** | 顧問主導，協會配合 |
| **投入** | 約 2 週，其中顧問實際工時集中在訪談與查證 |
| **步驟** | ① 跑 `npo-org-brain` 逆向偵察 → ② 結構化訪談補缺 → ③ 事實庫逐條查證出處 → ④ 問出紅線 → ⑤ 語氣校準（給 3～5 則協會自己的貼文）→ ⑥ 匯入系統 → ⑦ 帶協會跑通第一則貼文 |
| **交付** | 協會腦五區塊建檔完成、一份「資料不一致清單」、第一則實際發出的貼文 |
| **收費** | 一次性導入費 |

**三個一定會卡住的地方**，導入報價要把時間算進去：

1. **事實庫查證最花時間。** 協會會說「我們服務超過一萬人」，但問到出處就沒有了。
   逐條要出處這件事，協會自己不會做，也不習慣被這樣問。
2. **紅線要問得出來。** 「你們什麼話不能說」這題，第一次問通常得到「沒有耶」。
   要靠具體情境逼出來（「如果我們寫『捐 500 元救一個孩子』可以嗎？」）。
3. **`npo-org-brain` 的逆向偵察會抓到協會自己的資料互相矛盾**——年報寫 12,480、官網寫 13,000。
   **那份不一致清單就是導入期最有說服力的交付物**，它證明了這件事非做不可。

### L2 工具訂閱 — 月費

| | |
|---|---|
| **誰做** | 協會自己 |
| **協會每週要付出** | 填 seed（今天發生什麼真事），約 10 分鐘 |
| **工具自動做** | 生成、守門、排程、成本記錄 |
| **交付** | 每週的社群內容、廣告文案、（pro）廣告圖與募款頁 |
| **收費** | 月費，分級見 §7 |

**這一層的成敗完全取決於一件事：協會有沒有人每週填 seed。** 見 §4。

---

### L3 年度顧問 — 年費

| | |
|---|---|
| **誰做** | 顧問 |
| **節奏** | 年度規劃工作坊 ×1 ＋ 季度檢視 ×3～4 ＋ 專案陪跑 |
| **載體** | M2 年度募款規劃（工作坊在線下做，成果存系統，季度回來檢視） |
| **交付** | 年度募款計畫、四大檔期配置、各季調整建議、給理監事會的成效報告 |
| **收費** | 年費 |

**這一層是定價權的來源。** 工具月費會被比價，年度顧問不會——因為賣的是判斷與陪跑。

## 3. 三方分工 ★ 這張表決定服務怎麼報價

| 事情 | 工具自動 | 顧問人工 | 協會自己 |
|---|:---:|:---:|:---:|
| 公開資料逆向偵察 | | ● | |
| 協會腦五區塊建檔 | | ● | ○ 受訪 |
| **事實庫查證出處** | | ● | ○ 提供文件 |
| 問出紅線 | | ● | ○ 受訪 |
| 語氣校準（給範例貼文） | | ○ | ● |
| **每週填 seed** | | | ● |
| 生成內容／文案／圖 | ● | | |
| **合規守門** | ● | | |
| 核准與發布 | | | ● |
| 排程推送 | ● | | |
| 拉廣告數據 | ● | | |
| 月報彙整 | ● | | ○ 對外報告 |
| 健診解讀與行動建議 | | ● | |
| 年度募款規劃 | ○ 產出草案 | ● 帶工作坊 | ○ 參與 |
| 季度檢視與調整 | ○ 提供數據 | ● | ○ 參與 |
| **事實庫年度更新** | ○ 提醒 | ○ | ● |
| 勸募字號換證提醒 | ● | ○ 協助 | ● 實際申請 |

●＝主責　○＝參與

**讀這張表要看三件事：**

1. **顧問的工時集中在導入期與年度／季度節點**，日常不需要顧問。
   這決定了一個顧問可以帶多少家協會——服務可規模化的關鍵在這裡。
2. **守門完全自動**。這是產品價值的核心，而它不吃顧問工時。
3. **有兩件事只有協會能做，工具與顧問都代勞不了**：填 seed、核准發布。
   這兩件事做不到，服務就交付不了——所以導入期必須把這兩個習慣建立起來。

## 4. 最大的服務風險：沒人填 seed ★

產品的硬規則是「無 seed 不生成」——使用者必須先填「今天實際發生了什麼真事」。
這條規則在產品面完全正確（模板是骨，肉一定要是真的），但在**服務面它是最大的單點失敗**：

> 協會的小編兼社工兼行政，週三下午三點，手上有五件事。
> 打開工具看到一個空白的 seed 欄位，寫不出來，關掉。下週再說。
> **工具沒有輸入，就沒有輸出，兩個月後退訂。**

服務架構必須正面回答這題。三種作法，建議三種都做：

| 作法 | 說明 | 誰負責 |
|---|---|---|
| **建立固定時點** | 導入期就綁定「每週某個既有會議之後」填，不要新增一個習慣，寄生在既有習慣上 | 顧問在導入期設定 |
| **降低填寫門檻** | seed 不是要寫文案，是回答「這週誰來了／發生什麼／誰說了什麼」。給範例、給提示問句 | 產品（UI 文案） |
| **顧問代撈** | 從協會的週會記錄、LINE 群、活動照片裡撈素材。**這本身就是顧問服務可以賣的一項** | 顧問（可作為加值方案） |

第三種特別值得注意：**「幫你把週會記錄變成一週內容」是一個可以獨立賣的服務**，
而且它剛好解決了工具最大的失效原因。

## 5. 服務年曆（對齊台灣 NPO 的節奏）

| 時點 | 事件 | 服務動作 | 用到 |
|---|---|---|---|
| **1–2 月** | 春節前募款檔期 | 年度規劃工作坊；春節檔期內容 | M2 · M3 |
| **3–4 月** | 上年度年報出爐 | **事實庫年度更新**（新的服務人次、財報數字） | M-1 |
| **5 月** | 綜所稅申報 | 提醒捐款人抵稅效果；捐款人回訪素材 | M3 · M4 |
| **Q1 末** | | 第一季檢視 | M2 · M6 |
| **6–8 月** | 年中檔期 | 中期成效檢視、策略微調 | M6 · M2 |
| **9–11 月** | | 年底檔期備料：素材、頁面、廣告先做好 | M4 · M5 · M7 |
| **12 月** | **年底抵稅檔期（全年最大峰）** | 全力衝刺；這個月的成效決定續約談判的籌碼 | 全部 |
| **字號到期前 3 個月** | 勸募許可換證 | 系統提醒 → 顧問協助準備 | M-1 |

**12 月是全年最大峰**（`skills-inventory.md` §3.3 紅線也這樣寫）。
服務設計上要注意：**年約的起訖點最好避開 12 月**——不要在客戶最忙、也最看得出成效的月份談續約，
建議把年約週期設在 Q1 或 Q2，讓 12 月的成績成為續約談判的證據而不是干擾。

## 6. 續約鉤子：勸募字號到期 ★

`org_permits` 有 `valid_to` 欄位。台灣的勸募許可是**有效期制、每年要重新申請**的。

這是一個天然的年度服務節點，而且它是**強制發生**的——協會不能不換證。

服務上要做三件事：

1. 系統在字號到期前自動提醒（這是產品功能，成本近零）
2. 顧問在那個時點主動接觸，協助準備換證資料
3. **把換證時點設計成年約的自然續期時點**

其他續約理由（成效變好、報告好用）都是軟的，會被砍價。
**換證是硬的**——它每年一定發生，而且協會會希望有人幫忙。

> 順帶一提：這也是 G3 守門的商業價值。字號過期還在對外募款是行政違規，
> 系統擋下來的那一次，就是續約談判裡最有力的一句話。

## 7. 方案分級

`orgs.plan` 目前定義為 `trial / standard / pro`（`architecture.md` §4.1）。
`consulting_until` 另外記年度顧問到期日——**顧問是獨立的一條線，不是方案的一級**。

建議的分級邏輯（數字待定，見 §9）：

| | trial | standard | pro |
|---|---|---|---|
| 定位 | 健診後的體驗 | 日常內容產能 | 完整行銷作業 |
| 模組 | M3 | M3 · M4 · M1 | 全部（＋M5 M6 M7） |
| 生成額度 | 低 | 中 | 高 |
| 圖片額度 | — | — | 有 |
| 使用者席次 | 1 | 2–3 | 5 |
| 守門 | **全部** | **全部** | **全部** |
| 期限 | 限時 | 月訂 | 月訂 |

**守門在每一級都是完整的，不能拿來當分級籌碼。**
這是產品的信任基礎，「便宜方案守門比較鬆」會直接毀掉整條產品線。

### 導入是必選，不是加購

建議：**第一年必含導入**，第二年起顧問可選。理由不是為了多收錢，是為了防止退訂——
沒有導入，協會腦是空的，工具產出全是 `【請補資料】`，客戶會在第二個月退訂並且到處說這工具不能用。

## 8. 交付物清單（客戶實際拿到什麼）

| 階段 | 交付物 | 形態 |
|---|---|---|
| 健診 | 募款健檢報告 | 文件 |
| 導入 | 協會腦建檔完成 | 系統內 |
| 導入 | **資料不一致清單** | 文件 |
| 導入 | 第一則實際發出的貼文 | 實績 |
| 每週 | 社群內容（含守門報告） | 系統內 |
| 每月 | 成效報告（理監事會可用） | 文件 |
| 每季 | 檢視結論與調整建議 | 文件 ＋ 系統內 |
| 每年 | 年度募款計畫 | 文件 ＋ 系統內可追蹤 |
| 隨時 | 待補圖清單（可直接交給攝影師） | 文件 |

**守門報告要被當成交付物看待**，不是系統日誌。
「本次檢查通過 6/6」這種東西是給理監事會看的，也是協會對捐款人交代的憑據。
