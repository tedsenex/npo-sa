# 系統自檢：缺什麼

**建立日期：2026-08-06**
**範圍**：法規、勸募條例、守門規則本身不在這次自檢範圍內。只看「這東西要能真的跑起來、真的賣得動，還缺什麼」。

---

## 結論先講

```
   ┌─────────────┐      ┌──────────────────┐      ┌─────────────┐
   │  事實庫怎麼  │      │   生成 + 守門     │      │  產出之後   │
   │  被填滿      │ ───▶ │   Generator      │ ───▶ │  怎麼走     │
   │             │      │   G1…G11         │      │             │
   │   ▓ 空的     │      │   ▓ 設計完整      │      │   ▓ 空的     │
   └─────────────┘      └──────────────────┘      └─────────────┘
```

**中間那段設計得很完整，兩頭都是空的。**

- **上游**：整個產品的價值建立在 `org_facts` 上，但沒有任何機制讓它被填滿。
  秘書長不會坐下來手動輸入 50 條「累計服務人次 = 12,480，出處：2025 年報 p.14」。
  事實庫是空的，系統就只會吐一堆 `【請補資料】`——**第一天就死在這裡**。
- **下游**：生成完存進 `content_items` 之後，審核、微調、重生成、發布、回饋，
  一個都沒定義。而 AI 產出永遠只有八成對，那兩成的修改動線才是使用者每天在做的事。

以下按「不補會出事」的程度排。

---

## A. 上游：協會腦的冷啟動 ★ 最大的缺口

### A1. 事實庫沒有匯入機制，這是產品的單點失敗

目前的設計是使用者在 `org/setup` 一條一條手填。實際上不會發生。

需要一條路徑：**上傳年報 / 貼官網網址 → LLM 抽出事實候選 → 人工逐條勾選確認 → 入庫**。
抽出來的每一條要自動帶出處（哪份文件第幾頁），這正好就是 `org_facts.source` 要的東西。

這個功能大到應該有自己的編號，它不是 `org/setup` 的一個小按鈕。
而且它本身就是很好的銷售 demo：**丟一份年報進去，三分鐘後協會腦就活了。**

> 附帶好處：抽取過程會發現協會自己的資料互相矛盾（年報寫 12,480、官網寫 13,000），
> 這個「不一致清單」本身就是顧問服務的第一份交付物。

### A2. 沒有 onboarding 動線

協會腦有五個區塊，新使用者進來看到五個空表單會直接關掉。
需要引導式流程（先填最少可用的、其餘可跳過）、進度指示（協會腦完成度 40%）、
以及**一組填好的範本協會**讓他改比較快。

### A3. `org_voice.sample_posts` 只有 3 則，且沒說怎麼用

是拿來當 few-shot 嗎？3 則夠嗎？隨著協會發文變多，表現好的貼文要不要自動回流成樣本？
現在這欄位存在但沒有被任何流程使用的定義。

---

## B. 下游：產出之後的動線

### B1. 沒有「重新生成」與「微調」★ 沒有這個產品不可用

現在只有一次性生成。實際使用一定是：

- 「這版太硬，語氣軟一點」
- 「開頭換一個」
- 「第三段刪掉」

需要 `regenerate`（同輸入重跑）與 `refine`（帶上一版 + 修改指令再生成）。
資料上要 `generations.parent_generation_id`，才知道哪幾版是同一次嘗試的迭代。

**順帶要決定：重生成算不算一次額度？** 這直接影響使用者行為與你的毛利。

### B2. 手動編輯是一條繞過守門的路

`content_items.body` 可以被使用者直接改。改完直接發布，就完全沒經過守門。
硬規則寫「不准有繞過 guardrail 的路徑」，這就是一條。

要補：**手改後存檔時重跑守門**（純程式那幾關成本近零，跑就是了）。
或至少標記「此版本經人工修改，未重新檢查」。

### B3. 審核流程沒有定義

`content_items.status` 有 draft / approved / scheduled / published，但沒定義：

- 誰能從 draft 推到 approved？（editor 自己核自己？）
- 被退回怎麼辦？有沒有退回意見？
- approved 之後又改了，要不要退回 draft 重審？

這是個 state machine，要畫清楚，否則每個模組會各實作各的。

### B4. 沒有回饋機制，等於沒有品質儀表 ★

`generations` 記了輸入輸出成本，但沒記**使用者覺得這則好不好、最後有沒有採用**。

沒有這個欄位，會有三個後果：

1. 架構書 §5.2 說「改 prompt 後品質變差可以回溯」——但沒有評判依據，回溯了也不知道哪版好。
2. 不知道七型範式哪型表現好，也不知道該不該調整配比。
3. 沒有東西可以拿去跟協會證明工具有用。

建議加 `rating`（好／普通／差）與 `was_used`（是否真的被採用）。
**「被採用率」是這個產品最重要的單一品質指標**，也是續約時最強的數字。

### B5. `content_items` 沒有發布結果

排程了、推了 Metricool，實際發布成功沒？貼文網址是什麼？沒有欄位。
M6 要把成效對回是哪一則貼文，也需要這個關聯（`published_url` / `external_post_id`）。

### B6. 沒有內容去重

系統每週生成內容，很容易一路寫同樣的東西——這是內容工具最常見的死法。
生成時應該把近 N 週的產出摘要餵進 context，明確要求避開已寫過的角度。

### B7. M3 叫「社群內容**排程**」，但排程功能不在任何一期

架構書 §7 說 M3 輸出接內容日曆，CLAUDE.md 的 P1 只做單篇生成。
「一次規劃一週」這個功能（你既有的 skill 都有）在哪一期？沒寫。

這個落差要補，不然 M3 上線後使用者會問「所以我還是要一天開一次？」

## C. 工程：會爆的

### C1. 守門的 LLM 呼叫失敗時要 fail-closed ★

G2、G6 靠 Haiku。那次呼叫超時或掛掉時怎麼辦？沒寫。

如果放行，護城河是紙做的——**只要在對的時機失敗，任何東西都能過**。
必須明確：守門失敗一律視為未通過，回傳 error 或標記為需人工複核，絕不放行。

### C2. 沒有冪等性，連點兩次燒兩次錢

生成按鈕沒有防重複機制。需要 idempotency key（或至少前端鎖 + server 端短時間去重）。

### C3. 長時間生成沒有處理，M5 / M7 一定會超時

M7 一頁十二個區塊要逐區塊生成，M5 生圖是非同步的。
serverless function 有執行時間上限，這兩個一定撞得到。

架構書寫了「背景任務 Vercel Cron + DB 佇列」，但沒說：哪些工作走佇列、
任務狀態怎麼存、前端怎麼輪詢進度、失敗怎麼重試。
**M7 的逐區塊生成在設計階段就該想清楚，不是 P4 再說。**

### C4. 守門沒有測試 = 沒有護城河 ★

護城河的正確性完全沒有驗證計畫。G1、G5 是純函式，最好測，也最該測：

- G1 的數字辨識：中文數字（三千）、千分位（12,480）、單位（人次／公斤）、
  範圍（3～5 人）、約數（近 5,000）、序數（第 3 屆）、百分比
- G5 的繁簡與詞彙比對

需要一組**黃金測試集**：一批標好「該擋／該放」的樣本，每次改動都跑。
這份測試集本身也是資產，可以拿給協會看「我們檢查這些情況」。

### C5. 沒有開發環境的 LLM mock

T11 要種假資料端到端跑通，但沒說開發時怎麼避免每次都真的燒 API。
需要一個 fixture 模式：固定輸入回固定輸出，讓守門與 UI 可以離線開發與測試。

### C6. 環境變數清單不完整

CLAUDE.md 列了五個。P1 至少還會用到 app URL（magic link 的 redirect 目標）。
之後還有 Higgsfield、Metricool、Cron secret。現在不補沒關係，但要知道清單會長。

## D. 商業：會影響收錢的

### D1. 有記帳，但沒有煞車 ★

`generations.cost_usd` 記了每一次的成本，但沒有任何上限機制。
單一協會誤用或惡意使用，可以直接燒爆你的 API 帳單，而你會在月結時才發現。

需要兩層 hard cap：**org 級**（超過月度成本上限就停止生成）與
**全站級**（總量異常就全域降級）。這件事 P1 就該有，不是規模化才做。

### D2. 額度的定義沒說清楚

`usage_quotas` 有欄位，但沒定義：額度用完是硬擋還是降級？超額計費嗎？
守門用掉的 Haiku 算不算一次？重生成算不算一次？

這幾題不定，計價頁就寫不出來。

### D3. 沒有金流

P2 的目標是「可以開始收月費」，但訂閱、發票、方案升降級一個都沒設計。
台灣 NPO 常需要**匯款＋紙本收據**，不是所有協會都刷卡——這會影響金流選型。

### D4. 顧問視角排 P5，但顧問是一半的收入

商業模式是「工具月費 + 年度顧問」，顧問服務撐起定價權。
但 `consultant` 角色與跨客戶視角排在 P5 最後一期。

顧問要同時看多個協會，至少需要：org 切換器、跨協會的待辦清單、
「這個客戶這季做了什麼」的彙整頁。**建議把最小可用的顧問視角提前到 P3**，
跟 M2 年度規劃一起——那本來就是顧問在用的模組。

### D5. 沒有多協會切換 UI

顧問一定屬於多個 org，owner 也可能（總會／分會）。org switcher 沒被提過。

## E. 資料模型直接漏掉的欄位

| 表 | 缺什麼 | 為什麼 |
|---|---|---|
| `generations` | `prompt_version` | 架構書 §5.2 明說要記用了哪版 prompt，但 §4.2 的表沒這欄。文件自己內部矛盾 |
| `generations` | `parent_generation_id` | 重生成／微調的迭代鏈（B1） |
| `generations` | `rating` / `was_used` | 品質儀表（B4） |
| `org_facts` | `expires_at` 或 `review_after` | 只有 `verified_at`，沒有「多久算過期」。2023 年查核的數字 2026 年照樣放行 |
| `content_items` | `published_url` / `external_post_id` | 發布結果與成效對帳（B5） |
| `content_items` | `edited_by_human` | 標記人工修改過，供 B2 判斷要不要重跑守門 |
| 全表 | **稽核軌跡** | 誰改了事實庫、誰改了紅線、誰把貼文改成 published。NPO 要對理監事會交代；而且紅線被改掉等於守門被繞過 |

## F. 建議優先序

### 動 P1 之前就要決定的

1. **C1 守門 fail-closed** — 一行決定，但寫錯就沒有護城河
2. **D1 成本 hard cap** — 沒有這個，任何一次意外都可能是四位數美金
3. **B4 回饋欄位** — 現在加是一個欄位，之後補是資料斷層
4. **E 那幾個欄位** — schema 一旦跑過 migration 就有成本，趁 T2 一次補齊

### P1 範圍內就該做的

5. **C4 守門黃金測試集** — 跟 T7 一起寫，不要事後補
6. **B1 重新生成／微調** — 沒有這個 T9 的頁面實際不可用
7. **B2 手改後重跑守門** — 這是守門唯一的漏洞
8. **C2 冪等性** — 便宜，且會直接省錢

### P1 之後、但比現有排期更早

9. **A1 事實庫匯入** — 這是整個產品能不能被導入的關鍵，建議排 P2 開頭

11. **B7 週排程** — M3 的名字承諾了這件事
12. **D4 顧問視角提前到 P3** — 對齊商業模式
13. **C3 非同步任務框架** — 在動 M5/M7 之前

### 早晚要做

    D2 額度定義、D3 金流、D5 org 切換、C5 LLM mock、C6 環境變數

## G. 一個沒被講出來的產品判斷

這份自檢裡有八成的缺口，都指向同一件事：

**目前的文件把系統想成「一台生成機器」，但實際要賣的是「一套工作流程」。**

生成只是中間一步。真正決定使用者會不會續約的是：
資料進得來、產出改得動、成效看得到、顧問跟得上。
這四件事現在都沒有設計。

M3 能生出一則合規貼文，是技術風險過關。
但**技術風險過關不等於產品可用**——中間還隔著上面這一整排東西。
