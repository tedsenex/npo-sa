**要看懂三件事：**

1. **協會腦在最下面，不是設定頁，是原料庫。** 沒有模組可以繞過它自己編數字。
2. **守門在中間，橫切所有模組。** 每個模組的產出都要穿過同一道閘門才能落庫。
3. **這是一個閉環。** M6 的數據回到 M1/M2，年度顧問服務就是靠這個環續約。

## 2. 功能分層

### L0 帳號與租戶（平台底座）

| 功能 | 說明 |
|---|---|
| 登入 | Supabase Auth Email Magic Link。NPO 使用者不擅長記密碼 |
| 建立／加入協會 | 首次登入建 org + owner membership |
| 成員與角色 | owner / editor / viewer / consultant |
| 方案與額度 | `plan`（trial/standard/pro）、`usage_quotas` 月額度、`consulting_until` 顧問到期日 |
| 租戶隔離 | 每張表 RLS，policy 統一。**寫錯就是資料外洩** |

### L1 協會腦 M-1（一次建檔，七個模組共用）

五個區塊，對應 `org/setup` 的五個分頁：

| # | 區塊 | 表 | 這塊資料被誰用 |
|---|---|---|---|
| ① | **組織身分** 全名／簡稱／立案字號／主管機關 | `orgs` | 所有對外產出的署名；M5 圖上要寫死全名 |
| ② | **勸募許可** 字號／效期／核准用途／目標金額 | `org_permits` | G3 守門；M5 圖上標字號；M2 掛檔期 |
| ③ | **事實庫** key／value／出處／查核日／啟用 | `org_facts` | **G1 守門的唯一比對來源**；所有模組的數字都得從這裡來 |
| ④ | **紅線** 規則／嚴重度 | `org_redlines` | G2 守門 |
| ⑤ | **品牌語氣** tone／禁用詞／範例貼文／CI 色／logo／圖庫 | `org_voice` | 所有生成的語氣校準；M5/M7 的視覺 token |

> ③ 是整個產品的地基。事實庫空的，系統就只能產出一堆 `【請補資料】`。
> **導入期最該花力氣的不是教使用者用工具，是陪他把事實庫填滿。**

### L2 生成核心（所有模組共用的引擎）

| 功能 | 說明 |
|---|---|
| Generator 註冊 | 每模組一個，統一 `inputSchema` / `outputSchema` / `promptPack` / `guardrails` / `estimateCost` |
| Prompt Pack 版本管理 | `prompts/{module}/v1.md`，`generations` 記用哪版 → 改壞可回溯 |
| Context 組裝 | 協會腦五塊 → prompt context。這段是共用的，模組不各寫各的 |
| LLM 呼叫 | Anthropic，**只在 server**，強制結構化輸出 |
| 成本記帳 | token 進出與 `cost_usd` 逐次記錄 |
| 額度檢查 | 生成前檢查 `usage_quotas`，超額擋下 |

**新增模組 = 新增一個 Generator，不動框架。** 這是七個模組能一路複製下去的原因。

### L3 合規守門 M0（橫切層，護城河）

按**實作方式**分三類，決定成本與難度：

| 類型 | 守門 | 實作 | 成本 |
|---|---|---|---|
| 純程式（字典＋正則） | G1 事實核對、G5 用語檢查、G7 進度時效、G8 consent 檢查、G11 AI 標示 | 本地比對 | 近零 |
| 資料查核（查 DB） | G3 勸募字號、G9 換算來源、G10 服務數據 | 對 `org_permits` / `org_facts` | 近零 |
| 語意判斷（LLM） | G2 紅線比對、G6 禁用句型 | Haiku | 每次生成的附加成本 |

| # | 守門 | 處置 | 適用模組 |
|---|---|---|---|
| G1 | 事實核對：數字須在 `org_facts`，否則換 `【請補資料】` | block | 全部 |
| G2 | 紅線比對：掃 `org_redlines` | block / warn | 全部 |
| G3 | 勸募字號：須存在且未過期 | block | 全部 |
| G4 | AI 人像標示：生圖含人像強制附註 | 自動補 | M5 |
| G5 | 用語檢查：簡體字、大陸用語字典 | 自動改 + 提示 | 全部 |
| G6 | 禁用句型：「不是 X 而是 Y」（listicle 除外） | warn | 全部 |
| G7 | 進度數字須有 `updated_at`，逾 30 天不顯示 | block | M7 |
| G8 | `testimony` 無 `consent_note` 不准發布 | block | M7 |
| G9 | 換算式數字須有協會確認來源 | block | M7 |
| G10 | 頁面服務數據須來自 `org_facts` | block | M7 |
| G11 | AI 生成圖須帶 `is_ai` 並自動標示 | 自動補 | M5 / M7 |

**守門報告是產品的行銷素材**：前端顯示「本次檢查通過 6/6」，這是理監事會最想看的東西。

### L4 七個功能模組

按**使用頻率**分三組——這決定了 UI 動線該把誰放前面：

| 組別 | 頻率 | 模組 |
|---|---|---|
| **診斷與規劃** | 年度／季度一次 | M1 行銷健診、M2 年度募款規劃 |
| **日常產出** | 每週 | M3 社群內容、M4 廣告文案、M5 廣告圖片、M7 募款銷售頁 |
| **回看檢視** | 每月 | M6 廣告數據儀表板 |

### L5 產出管理

| 功能 | 說明 | 表 |
|---|---|---|
| 產出歷史 | 每次生成的輸入／輸出／守門報告／模型／成本 | `generations` |
| 內容日曆 | 草稿 → 核准 → 排程 → 發布 | `content_items` |
| 素材庫 | 文案、圖片、銷售頁 | `ad_copies` / `ad_images` / `landing_pages` |
| 外推 | 排程推送 Metricool | — |
| 額度看板 | 本月已用生成數／圖片數 | `usage_quotas` |

## 4. 模組依賴：`campaigns` 是樞紐

七個模組不是七個平行的工具，它們串成一條線：

```
M1 診斷（找出缺口）
   ↓ 缺口清單
M2 規劃（訂年度目標與檔期）
   ↓ 產出 campaigns ★
   ├─ M3 內容 ─┐
   ├─ M4 文案 ─┤
   ├─ M5 圖片 ─┼─→ 都掛在同一個 campaign 底下
   └─ M7 銷售頁┘
   ↓ 投放
M6 數據（收成效）
   ↓ 回饋
回到 M1 / M2
```

`campaigns` 同時被 `content_items`、`ad_copies`、`ad_images`、`landing_pages` 參照，
並且 `campaigns.permit_id` 掛勸募許可——**一個檔期用哪張字號，是從這裡決定的**。

**這對實作的意涵**：`campaigns` 排在 P3（M2 那期），但 P1/P2 的產出表已經要預留關聯。
關聯欄位什麼時候加，見 `open-questions.md` B4。

## 7. 功能 × 角色

`memberships.role` 四種角色，各自看得到什麼：

| 功能 | owner | editor | viewer | consultant |
|---|---|---|---|---|
| 讀協會腦 | ✓ | ✓ | ✓ | ✓ |
| 改組織身分／勸募許可（法遵資料） | ✓ | — | — | — |
| 改事實庫／紅線／語氣 | ✓ | ✓ | — | 建議可 |
| 執行生成 | ✓ | ✓ | — | ✓ |
| 核准／排程／發布 | ✓ | ✓ | — | — |
| 看守門報告 | ✓ | ✓ | ✓ | ✓ |
| 看成本與額度 | ✓ | — | — | ✓ |
| 看 LLM 原始輸出（守門前） | ✓ | — | — | ✓ |
| 邀請成員／改方案 | ✓ | — | — | — |

**兩個設計理由**：

1. **法遵資料（組織身分、勸募許可）只有 owner 能改。** 小編改錯勸募字號是行政違規，
   這欄位不該讓日常操作的人碰得到。
2. **守門前的原始輸出只有 owner / consultant 看得到。** 原始輸出裡可能有被 G1 遮掉的
   未查證數字，讓一般編輯看到等於留了一條複製貼上繞過守門的路。

> 這張表是**建議值**，`architecture.md` 只定義了四種 role 的名字沒定義權限，
> P5 才正式做權限系統。P1 只需要 owner 一種角色能跑通即可。
